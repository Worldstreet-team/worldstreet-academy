# QA notes for Owen — `blueprint/complete`, 2026-10-22

Found in a local run of `blueprint/complete` at `aebf161` (`dev:mock`, local MongoDB, a stub for the wallet API) by Amirize's QA session. Issues 1–9 from that run are fixed in the same working tree. The four below were left for you to decide.

**Status, 2026-10-23:** 11, 12 and 13 are fixed on `blueprint/complete`. 10 stays as it is: the owner confirmed ESPEE sales record no instructor earning.

## 10. ESPEE sales pay the instructor nothing (kept: owner's rule)

`adminApproveEspeePayment` creates the order and the enrollment, and the approval dialog says "No instructor earning is recorded for ESPEE payments." A program sold through ESPEE earns its instructor $0, while the same sale through the wallet earns them 85%. If that's the owner's rule, it may be worth stating where instructors can see it. If not, ESPEE approvals need an `Earning` row, and refunds need a clawback path for it.

## 11. A double refund isn't blocked atomically (fixed)

`refundEnrollment` (`lib/actions/earnings.ts`) reads `enrollment.status`, calls the wallet, then saves `status: "refunded"`. Two clicks that arrive together both pass the status check. The wallet refund is idempotent, so no money moves twice. The rest isn't, though: `clawBack` can write two `adjustment` rows for a cleared earning, and `enrolledCount` / `instructorProfile.totalStudents` drop by 2. Claiming the row first would close the gap, for example `Enrollment.findOneAndUpdate({ _id, status: { $ne: "refunded" } }, …)`. It's admin-only, so the risk is low.

## 12. Saving the course editor resets every student's progress (fixed)

`updateCourse` (`lib/actions/instructor.ts`, "Delete existing lessons and recreate") runs `Lesson.deleteMany` and then `insertMany` on every save. Each lesson gets a new `_id`. Everything keyed on the old ids is orphaned: `Enrollment.completedLessons`, `WatchProgress`, bookmarks and lesson knowledge-check exams (`Exam.lesson`). On a live program, one editor save puts every learner back at 0% for completed lessons and loses their resume positions. Your QA plans already warn testers not to POST the editor for courses with lessons. This is the production version of the same problem. The fix is to upsert lessons by id: the editor already carries `tempId`, so it can carry the real `_id` for existing lessons.

This was found by reading the code. It wasn't reproduced at runtime.

## 13. Upload actions have no auth check (fixed)

None of the exports in `lib/actions/upload.ts` call `getCurrentUser()`: `getImageUploadUrl`, `getVideoUploadUrl`, `getAudioUploadUrl`, `getDocumentUploadUrl` and `deleteUploadedFile`. Server actions can be called by anyone who has the action id, which ships in the client bundle. That means:

- **Uploads.** Anyone, signed in or not, can mint presigned PUT URLs into the public bucket.
- **Deletes.** `deleteUploadedFile(key)` deletes any key in the public bucket. Keys are visible in every thumbnail and video URL on public pages, so a visitor could delete course art and lesson videos.

At minimum, require a signed-in user for the upload URLs. Restrict `deleteUploadedFile` to keys the caller owns, or to admins.
